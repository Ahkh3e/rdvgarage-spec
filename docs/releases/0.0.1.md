Smallest usable slice: invite in, make an account, join a crew, go live on the map, see this week's top speed leaderboard.

## Weekly top speed leaderboard

- Each live session records the member's max speed. The leaderboard shows each member's best session max this week.
- A week starts Monday 00:00 America/Toronto and ends at the next Monday 00:00, then resets.
- A session that crosses the boundary is split into one summary per week, so each week has its own max speed. A late upload is placed by the timestamps of its readings.
- Per crew view: ranked members with handle, avatar, top speed, and the day it was set.
- Speed is recorded only while live. No live session, no entry.
- Implausible readings (GPS spikes) are discarded; rule set during build.
- Speed is shown on the leaderboard after the session, not as a live number on the map.
- This reverses the stats.md note against speed-based stats; see decision 0007.

## Architecture: modular by design

Goal: add or remove any feature without a rewrite.

- Each feature is a self-contained module: its own UI, state, and data access. Modules do not import each other.
- Modules talk through small shared contracts in a core layer: Session (current user), CrewContext (selected crews), LocationStream (live positions), Events (typed app events).
- Modules register themselves. Each module exposes one entry point that registers its own tabs, routes, and event handlers with the shell's registry at launch. The shell knows no module's internals and has no per-feature wiring.
- Adding a module means adding its package and its entry point to the app target's module list. Removing it means deleting that entry. Swift cannot discover packages at runtime, so that one list is the only central place.
- Features sit behind flags so a module can ship dark or be pulled without a release.
- The weekly leaderboard consumes session events from Live location; it holds its own data. Live location does not know the leaderboard exists. A future stats module consumes the same events.
- The Accounts module talks to our own user service behind a thin interface, so the credential method can change without touching other modules.
- Backend mirrors this: one service area per module, shared only by identity and crew membership.

### iOS structure

- Swift packages per module: Core, Referral, Accounts, Crews, Map, LiveLocation, Leaderboard, plus the App target that wires them.
- SwiftUI, with module entry points exposed as plain views and a registration function.
- Dependencies injected through the Core contracts, never through singletons.

## Acceptance

- New user opens an invite link, registers, sets a handle, and lands on My Crews.
- User creates a crew, shares its link; a second user joins.
- Both select the crew, go live, and see each other moving on the map.
- Leaderboard lists both with this week's top speeds.
- Disabling the leaderboard flag removes it with no other module affected.
